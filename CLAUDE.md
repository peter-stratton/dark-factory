# CLAUDE.md — Standing Orders for Agents

This file contains rules and conventions that all agents (human or AI) must
follow when working on the dark-factory codebase.

## Build and Test Commands

```bash
# Run all tests
go test ./...

# Build the binary
go build -o bin/godark ./cmd/godark

# Cross-compile for Linux (CI target)
GOOS=linux GOARCH=arm64 go build -o bin/godark ./cmd/godark

# Vet and lint
go vet ./...
```

## Protected Paths

These paths must **never** be modified by implementing agents (Agent 1).
Only humans may edit them.

- `CLAUDE.md` — this file
- `tests/scenarios/` — human-authored scenario specs

## Project Layout

```
cmd/godark/          CLI entry point
internal/cmd/        Cobra command definitions
internal/config/     YAML config loading and validation
internal/deps/       Dependency parsing and resolution
internal/github/     GitHub API interactions (via gh CLI)
internal/logging/    Structured logging (slog + JSON file)
internal/orchestrator/ Main orchestration loop
tests/scenarios/     Human-authored scenario specs (markdown)
tests/review/        Ephemeral review tests (generated by Agent 2, gitignored)
docs/                Project documentation and planning
```

## Coding Conventions

- **Go version**: See `.tool-versions` for the active Go version.
- **Module path**: `github.com/phs/dark-factory`
- **Test files**: Place `foo_test.go` next to `foo.go` in the same package.
- **Error handling**: Wrap errors with `fmt.Errorf("context: %w", err)`.
- **Logging**: Use `log/slog` with structured fields. Do not use `log.Printf`.
- **CLI framework**: Cobra (`github.com/spf13/cobra`).
- **Config format**: YAML via `gopkg.in/yaml.v3`.
- **No global state**: Pass dependencies (logger, config) explicitly.
- **External commands**: Use the `CommandRunner` variable pattern from
  `internal/github/issues.go` so commands can be stubbed in tests.

## Git Workflow

- Never commit directly to `main`. Always use feature branches.
- Branch names: `<issue-number>-<short-slug>` (e.g., `7-claude-md-scenario-specs`).
- Commit messages: Include `Closes #N` or `Fixes #N` to auto-close issues.
- PRs: Must include `Closes #N` in the body.

## Scenario Spec Format

Scenario specs live in `tests/scenarios/*.md` and follow this format:

```markdown
# Scenario: Feature name

Relates to: Issue #N

## Setup
- Description of test fixture state

## Cases

### Case name
Description of what to do.
- Expected outcome 1
- Expected outcome 2
```

The `Relates to: Issue #N` line links specs to issues. A spec can relate to
multiple issues, and an issue can have multiple related specs.
